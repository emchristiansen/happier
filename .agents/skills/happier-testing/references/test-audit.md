# Happier Test Audit And Cleanup

Use this mode only for an explicit audit, pruning, consolidation, or test-infrastructure cleanup request. Ordinary TDD does not require a campaign ledger.

## Choose a bounded campaign

Audit one canonical owner, harness family, package, or coherent test lane at a time. Record the observed source/HEAD basis and current dirty state. Do not turn the entire monorepo into one mass-deletion campaign or create a permanent test registry.

Classify candidates temporarily:

- `R` — retain: distinct observable, compatibility, security, platform, package, migration, release, or recovery proof;
- `F` — fix: valuable contract, but the assertion, fixture, harness, selector, wiring, or observation method is defective;
- `C` — consolidate: preserve the contract at one stronger canonical keeper and remove weaker parallel proof;
- `D` — delete: no material contract, unreachable scenario, vacuous assertion, obsolete process artifact, or completely subsumed proof.

For every `C` or `D`, name the detectable regression, non-test caller or test-only seam, stronger keeper, relevant history, and focused validation. Size, mock count, source inspection, timeout length, or slowness alone is never deletion evidence.

## Automate the mechanical work

Prefer existing repository generators, migration scripts, fixture factories, and testkit codemods. Use an AST-aware codemod when syntax or imports vary; use bounded structured replacement only for uniform text/configuration.

Extend the existing owners instead of adding a parallel audit toolchain:

- `scripts/testing/lib/testPolicyRules.ts` owns repository test-policy findings;
- `scripts/testing/migrations/lib/inventoryDuplicatePatterns.ts` owns duplicate-pattern inventory;
- `scripts/testing/migrations/lib/rewriteImports.ts` and neighboring migration modules own mechanical rewrites.

Add new detection or transformation there when it fits their contracts, with owner-level tests beside the module. Create another tool only when the existing owners cannot represent the required input or output without distorting their purpose.

Good codemod targets include:

- replacing a known inline boundary-mock family with its canonical testkit factory;
- rewriting imports after a canonical helper consolidation;
- converting repeated declarative conformance cases into data rows without changing assertions;
- removing a test-only export after a complete consumer search proves every retained test uses the real owner;
- updating a mechanically derived lane or inventory generated by one canonical producer.

Do not codemod decisions about whether two scenarios protect the same contract, whether a compatibility vector is released, whether a platform lane is redundant, or which owner is authoritative.

Before a broad transformation:

1. enumerate the exact match set and exclusions;
2. prove one representative input/output transformation;
3. run in dry-run or preview mode;
4. inspect representative and aggregate diffs;
5. verify no unmatched old pattern and no unintended new match remains;
6. run the codemod/tool's focused tests, retained keeper tests, and the affected package/lane.

Keep smell analyzers report-only initially. Useful candidates include exact source/prose/import greps, copied inventories, test-only production seams, internal-domain mocks, assertion-free probes, incidental total call counts, and changed timeout/retry literals. Promote an analyzer to enforcement only after its false-positive set is understood and legitimate exceptions are owner-local.

## Preserve the right proof

Retain public API/ABI, protocol, crypto, persistence, migration, package, generated-output, trust/permission, installer/update, platform, accessibility, compatibility, artifact, signing, and real lifecycle contracts when they provide independent proof. Consolidate scaffolding and duplicated fixtures before removing these scenarios.

Use the strongest practical boundary as keeper: real owner behavior over source spelling, real SQLite/Fastify over a fake internal repository, packed artifact over working-tree existence, provenance-pinned predecessor vector over a schema reconstructed from current types, and real process/transport behavior over internal call transcripts.

## Validation and measurement

Use focused RED/GREEN while moving a contract, then the owner suite and affected package/lane. Run the full exact-SHA profile once after a coherent campaign batch, not after each deletion. Measure setup/install, test execution, critical-path time, runner-minutes, retries/flakes, and shard balance separately; do not report raw deleted LOC or test count as the success metric.

The campaign is complete when every changed contract has one named keeper, obsolete seams and parallel helpers are removed, affected validation is terminal, and residual release-only or platform evidence is explicit.
